Quark — La Biblia

Framework lite para enseñar a programar en Unity con buenas prácticas.

Este documento es la única fuente de verdad del diseño de Quark: sus principios, sus bases y su visión. Todo lo que se construya de acá a 10 años se mide contra esta página. Si algo la contradice, o se corrige el código, o se corrige la Biblia — nunca conviven en desacuerdo.

Por TXMSKA (Tomás Daniel Tasca) · txmska.com

Manifiesto

Quark existe para enseñar buenas prácticas con la menor cantidad de código posible. No compite con frameworks grandes: compite con la confusión.

  • Cada clase debe poder leerse completa en una pantalla.
  • Cada nombre debe enseñar qué es la cosa (los alumnos aprenden de los nombres).
  • El framework se enseña a sí mismo: sus propias clases usan sus propios patrones (Atom se compone con Addons; Nucleus existe porque el pipeline se repetía 3 veces — composición aplicada al propio problema).
  • Sostenible por una sola persona, a largo plazo. La rama release siempre queda usable de punta a punta.

Los 10 Mandamientos

  1. Reusarás antes de crear. Librería estándar → función de Unity → paquete ya instalado → recién ahí, código nuevo.
  2. No construirás lo que no necesitás (YAGNI). Mencionar una idea no es pedirla: la visión se anota, el código se escribe cuando de verdad hace falta.
  3. Menos código gana. Si un borrador más chico funciona, el grande se borra. Borrar antes que agregar.
  4. Todo es lazy. Los recursos se generan cuando un sistema los necesita (el Uid nace en su primer acceso), nunca "por las dudas".
  5. Compondrás, no heredarás. El comportamiento se arma con Addons y Mods. La herencia es solo para identidad (Entity, Prop, Service), no para features.
  6. El código habla; los comentarios callan. Sin comentarios narrativos, sin historia del fix. Solo invariantes no obvios o rarezas de Unity.
  7. Una línea si alcanza. One-liners salvo que de verdad se necesite más.
  8. Con Unity Objects, null explícito. Nada de ?. ni ?? sobre lo que herede de UnityEngine.Object (saltean el == sobrecargado y un objeto destruido pasa por vivo). Las clases planas sí pueden.
  9. Ni constantes de un solo uso, ni serialización prematura. El literal va inline salvo que el nombre documente un significado compartido; un campo entra al inspector cuando su valor importa de verdad.
  10. Documentarás solo lo terminado. El doc-pass llega cuando el script está listo — nunca mientras se desarrolla (los summaries engordan el archivo y marean).

Las tres bases

Todo lo que existe en un juego hecho con Quark es una de estas tres cosas. No hay una cuarta. Si parece que falta una categoría, en realidad falta un Addon o un Mod.

Entity : Identifiable

Cualquier personaje, jugador o no. Si "actúa" y "vive", es Entity.

Ej.: jugador, NPC, enemigo, mascota, boss, criatura.

Prop : Identifiable

Cualquier objeto de escena con comportamiento propio. Si "está" y hace algo, es Prop.

Ej.: puerta, cofre, palanca, item agarrable, trampa, antorcha.

Service : MonoBehaviour

Una implementación autónoma de escena, sin cuerpo. Un sistema que corre. Tiene Priority.

Ej.: spawner, director de audio, ciclo día/noche, score, guardado.

Guía de decisión

PreguntaRespuesta
¿Tiene cuerpo y actúa por sí mismo?Entity
¿Es una cosa tangible de la escena con comportamiento?Prop
¿Es un sistema invisible que corre en la escena?Service
¿Es comportamiento que pertenece a otro?Addon (parte interna) o Mod (pieza de escena que lo altera)
¿Orquesta todo el juego?GameManager (un Service singleton; Atom es el default)
Jerarquía completa: Identifiable → Entity / Prop · Service → GameManager → Atom. Eso es todo el árbol. Cualquier tentación de agregarle profundidad va contra el Mandamiento V.

Vocabulario

TipoQué es
IdentifiableRaíz con identidad: Id legible a mano (puede repetirse: "player", "crate") + Uid único auto-generado lazy.
EntityPersonaje (jugador o no).
PropObjeto de escena con comportamiento propio.

Nucleus<T>Clase plana sellada que empaqueta addons + mods + su ciclo de vida, UNA sola vez. Cada host la tiene como campo.
QuantumUtils static sin estado (generación de Uid anti-colisión, conexiones indirectas).

Tema de nombres: Quark → Atom → Quantum → Nucleus. La física para la infraestructura; nombres descriptivos y planos para lo que el alumno toca.

Capas y carpetas

Tres capas por nivel de abstracción. La dependencia va en una sola dirección (a futuro la fija un .asmdef por capa):

0 - ROOT static helpers sin estado (Quantum) ← no depende de nada 1 - CORE abstract los tipos base que se extienden ← usa ROOT 2 - EXTENSIONS concreto deriva de CORE: defaults, tutoriales ← usa CORE
  • 1 - CORE/ se subdivide por dominio: Identity/ (Identifiable, Entity, Prop) · Composition/ (Addon, Mod, Nucleus) · Management/ (GameManager, Service).
  • 2 - EXTENSIONS/ hoy: Atom.cs y Testing/. Acá viven los módulos y tutoriales por venir.
  • Los dominios nuevos (UI, Gameplay, Audio…) son subcarpetas dentro de la capa, on-demand — nunca capas nuevas.
  • Carpetas Editor/ (a cualquier profundidad) = código solo-editor, excluido del build.

Ciclo de vida (auto-init)

Nada se inicializa solo: siempre lo dispara su dueño. El owner delega en su Nucleus.

Awake → nucleus.Initialize(this) 1. addons de la lista → Initialize(owner) (los null se ignoran) 2. mods detectados → GetComponentsInChildren<Mod<T>>(true) (solo los que responden a ESTE owner: guard del padre más cercano) 3. cada mod → Initialize(owner) OnDestroy → nucleus.Teardown() (orden inverso: mods → addons)
Regla de oro de las subclases: si usás Awake, Start u OnDestroy, es override y llamás base. — el pipeline vive ahí.

El GameManager agrega su parte antes del base.Awake(): chequeo de duplicado (se autodestruye) → Instance = this → DontDestroyOnLoad.

Estilo de código

Regiones (componentes)

En este orden fijo; la región vacía se salta; línea en blanco tras #region X y antes de #endregion:

RegiónContenido
FIELDSVars y props serializadas (lo que ve el inspector).
LIFETIMEMensajes de Unity (Awake, OnEnable, Start, OnDestroy…).
APIMétodos / props públicos.
MISCPrivados.
  • Las vars no serializadas van al lado de la función que las usa, no en un bloque arriba.
  • Inspector prolijo sin Odin (repo público): atributos nativos — [Header], [Space], [Tooltip]. Agrupado tipo Odin recién si hace falta, vía custom editor.
  • Imitá siempre el código vecino (nombres, llaves, modificadores).

using System.Collections.Generic;

namespace Quark
{
    public static class Quantum
    {
        static readonly HashSet<string> uids = new();

        public static string NewUid()
        {
            string uid;
            do { uid = Guid.NewGuid().ToString(); }
            while (!uids.Add(uid));
            return uid;
        }
    }
}

using UnityEngine;

namespace Quark
{
    public abstract class GameManager : Service
    {
        #region LIFETIME

        protected override void Awake()
        {
            if (Instance != null) { Destroy(gameObject); return; }
            Instance = this;
            DontDestroyOnLoad(gameObject);
            base.Awake();
        }

        protected override void OnDestroy()
        {
            if (Instance == this) Instance = null;
            base.OnDestroy();
        }

        #endregion

        #region API

        public static GameManager Instance { get; private set; }

        #endregion
    }
}

1 - CORE/Composition/Nucleus.cs 
using System;
using System.Collections.Generic;
using System.Linq;
using UnityEngine;

namespace Quark
{
    [Serializable]
    public sealed class Nucleus<T> where T : Component
    {
        [SerializeReference] List<Addon<T>> addons = new();
        Mod<T>[] mods;

        public bool Initialized => mods != null;

        public void Initialize(T owner)
        {
            addons.ForEach(a => a?.Initialize(owner));
            mods = owner.GetComponentsInChildren<Mod<T>>(true)
                        .Where(m => m.GetComponentInParent<T>() == owner).ToArray();
            foreach (var m in mods) m.Initialize(owner);
        }

        public void Teardown()
        {
            if (mods == null) return;
            foreach (var m in mods) if (m != null) m.Teardown();
            addons.ForEach(a => a?.Teardown());
        }
    }
}

Por qué Nucleus existe: el pipeline addons+mods estaba copiado 3 veces (Entity, Prop, Service). En vez de herencia genérica (CRTP, ilegible para novatos) o un helper static (campos igual duplicados), se eligió composición: la lógica y el estado juntos, una sola vez, y cada host queda en 3 líneas. El framework aplicándose a sí mismo.
Detalles finos del Nucleus: el ?. sobre addons es legal (clases planas) y tolera los huecos null de la lista. El guard GetComponentInParent<T>() == owner evita que un owner anidado le "robe" los mods al de adentro. mods == null = nunca inicializado → Teardown no hace nada.

Editor / Drawer

Unity no trae selector de tipos para listas [SerializeReference] (el + mete null). Odin lo daba; acá es un PropertyDrawer propio, editor-only:

  • NucleusDrawer — aplana Nucleus > Addons a una lista "Addons" directa.
  • AddonDrawer — elemento null → botón "Select Addon…" → menú con los tipos concretos válidos para ese owner (TypeCache filtrado); al elegir: Activator.CreateInstance → managedReferenceValue. Elemento con valor → campos normales + botón para cambiar de tipo o volver a None.
1 - CORE/Composition/Editor/NucleusDrawer.cs 
using System;
using UnityEditor;
using UnityEngine;

namespace Quark
{
    [CustomPropertyDrawer(typeof(Nucleus<>))]
    sealed class NucleusDrawer : PropertyDrawer
    {
        public override float GetPropertyHeight(SerializedProperty property, GUIContent label) =>
            EditorGUI.GetPropertyHeight(property.FindPropertyRelative("addons"), label, true);

        public override void OnGUI(Rect position, SerializedProperty property, GUIContent label) =>
            EditorGUI.PropertyField(position, property.FindPropertyRelative("addons"), new GUIContent("Addons"), true);
    }

    [CustomPropertyDrawer(typeof(Addon<>), true)]
    sealed class AddonDrawer : PropertyDrawer
    {
        public override float GetPropertyHeight(SerializedProperty property, GUIContent label) =>
            property.managedReferenceValue == null
                ? EditorGUIUtility.singleLineHeight
                : EditorGUI.GetPropertyHeight(property, label, true);

        public override void OnGUI(Rect position, SerializedProperty property, GUIContent label)
        {
            var current = property.managedReferenceValue;

            if (current != null)
                EditorGUI.PropertyField(position, property, new GUIContent(current.GetType().Name), true);
            else
                EditorGUI.LabelField(position, label);

            var header = new Rect(position.x + EditorGUIUtility.labelWidth, position.y,
                                  position.width - EditorGUIUtility.labelWidth, EditorGUIUtility.singleLineHeight);
            if (EditorGUI.DropdownButton(header, new GUIContent(current == null ? "Select Addon…" : current.GetType().Name), FocusType.Keyboard))
                ShowMenu(property);
        }

        static void ShowMenu(SerializedProperty property)
        {
            var prop = property.Copy();
            var menu = new GenericMenu();
            var baseType = ResolveType(prop.managedReferenceFieldTypename);

            foreach (var type in TypeCache.GetTypesDerivedFrom(baseType))
            {
                if (type.IsAbstract || type.IsGenericTypeDefinition) continue;
                menu.AddItem(new GUIContent(type.Name), false, () => Assign(prop, Activator.CreateInstance(type)));
            }

            if (menu.GetItemCount() == 0) menu.AddDisabledItem(new GUIContent("No addons available"));
            menu.AddSeparator("");
            menu.AddItem(new GUIContent("None"), false, () => Assign(prop, null));
            menu.ShowAsContext();
        }

        static void Assign(SerializedProperty property, object value)
        {
            property.managedReferenceValue = value;
            property.serializedObject.ApplyModifiedProperties();
        }

        static Type ResolveType(string typename)
        {
            var parts = typename.Split(new[] { ' ' }, 2);
            return Type.GetType($"{parts[1]}, {parts[0]}");
        }
    }
}

Es IMGUI a propósito: para elementos managed-reference, UI Toolkit todavía renguea con el rebinding al cambiar de tipo. El agrupado visual tipo Odin del futuro sí irá en UI Toolkit.

Testing y primer tutorial

En 2 - EXTENSIONS/Testing/ viven los dobles de prueba: TestEntity, TestProp, TestService (hosts concretos vacíos) + un Addon y un Mod por base, que loguean su ciclo de vida. Este es, a la vez, el molde de todo tutorial futuro: así se extiende Quark.

Extender con un Addon (se agrega por inspector o por código) 
using System;
using UnityEngine;

namespace Quark
{
    [Serializable]
    public class TestEntityAddon : Addon<Entity>
    {
        public override void Initialize(Entity owner)
        {
            base.Initialize(owner);
            Debug.Log($"TestEntityAddon.Initialize → {owner.name}");
        }

        public override void Teardown()
        {
            Debug.Log($"TestEntityAddon.Teardown ← {Owner.name}");
            base.Teardown();
        }
    }
}
Extender con un Mod (componente en el GO del owner o un hijo) 
using UnityEngine;

namespace Quark
{
    public class TestEntityMod : Mod<Entity>
    {
        public override void Initialize(Entity owner)
        {
            base.Initialize(owner);
            Debug.Log($"TestEntityMod.Initialize → {owner.name}");
        }

        public override void Teardown()
        {
            Debug.Log($"TestEntityMod.Teardown ← {Owner.name}");
            base.Teardown();
        }
    }
}

La prueba canónica (escena Test)

  1. GameObject vacío → componente TestEntity.
  2. En su lista Addons: + → "Select Addon…" → TestEntityAddon.
  3. Al mismo GO (o un hijo): componente TestEntityMod.
  4. Play → consola: los dos Initialize. Stop → los dos Teardown (orden inverso).
  5. Repetí con Prop y Service. Un Prop solo ofrece Addons de Prop — el menú filtra por owner.
Las tres reglas que este molde enseña: override → base primero (en Teardown, base al final) · el owner es quien inicializa · Addon = capacidad interna, Mod = pieza de escena.

Protocolo de documentación

  • Cuándo: solo scripts terminados (Mandamiento X). Lo dispara el autor a mano ("docpass"), nunca automático.
  • Qué: (1) un XML <summary> corto de una línea por tipo terminado; (2) su página markdown en docs/.
  • Bilingüe: castellano primero (part.es.md), inglés opcional (part.en.md); lo que falte en inglés cae al español.
  • Plantilla de página: Título → descripción de una línea → "Qué es" → "Cuándo usarlo" → "Ejemplo" → "Recursos".
  • Sitio: esta página es la doc hasta que haya contenido real. El día del sitio: MkDocs + Material + mkdocs-static-i18n (~15 min: pip install mkdocs-material mkdocs-static-i18n → mkdocs.yml con idioma default es → mkdocs serve → mkdocs gh-deploy).

Workflow

  • Los commits los hace el autor, por GitHub Desktop. Ningún asistente commitea jamás.
  • Cero rastros de IA en el repo público: CLAUDE.md, .cursor/, .claude/ quedan fuera vía .git/info/exclude (local — no .gitignore, que es compartido y delataría los nombres).
  • Reglas de agente espejadas: CLAUDE.md (canónico) ↔ .cursor/rules/quark.mdc (mismo cuerpo + frontmatter). Tocás uno → actualizás el otro.
  • Rama release: lo estable y usable. Tags v0.1.0… para que los consumidores fijen versión.
  • Mensajes de commit en inglés, cortos: qué cambió y por qué.

Visión a futuro

Todo lo de abajo está anotado, no construido — Mandamiento II. Se construye el día que un sistema real lo necesite, en este orden de probabilidad:

PiezaDiseño previsto
Orquestación de ServicesEl GameManager alista los Services y los arranca ordenados por Priority (menor primero). El campo ya existe; la maquinaria (enlist/boot diferido) se probó y se retiró por no necesitarse aún.
Tick systemDentro del GameManager, estilo Universe de Cosmic: OnTick, TickRate, contador. Pausa = Time.timeScale nativo (reusar, no reinventar). Sería el único Update legítimo del framework.
Addons de AtomScenes (envuelve UnityEngine.SceneManagement.SceneManager, carga con sobrecargas) y Audio (música + SFX 2D/3D, estilo SFXEmitter). Quien necesite lógica propia subclasea el Addon, no crea un manager paralelo.
Dominios near-coreUI (Canvas/HUD/menús — un Flow simplificado) · Simulation · Localization (opcional, no dependencia dura del core) · Storage (inventario + persistencia; ahí se revisa si el Uid pasa a estable en edit-time).
PackagingUn .asmdef por capa (fija la dirección de dependencias) → CORE como package com.quark.core embebido en Packages/ → distribución por Git URL → OpenUPM al madurar. Package = distribución; asmdef = compilación.
EditorDrawer UI Toolkit con agrupado visual tipo Odin (cajas/foldouts), cuando IMGUI quede corto.
DocsSitio MkDocs bilingüe (es primero) en GitHub Pages, generado de docs/*.md.
Cómo decidir si algo entra a CORE: ¿es fundamental y depende solo de Unity? CORE. ¿Es opcional, de dominio puntual, o trae dependencia externa? EXTENSIONS (o package aparte). Ante la duda: EXTENSIONS — promover después es fácil; degradar rompe.
